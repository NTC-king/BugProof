BugProof runs one supported Python function in a separate browser origin. The model supplies a candidate; the application—not the model—compares actual results to explicit expectations.

Choose & run→Restricted worker→Compare & export

Three source stops

  1. src/App.tsx — run freezes the entered task/candidate, invokes both runs and rejects stale revisions. requestRepair sends only visible examples after consent.
  2. src/runner.ts — execute validates cross-origin messages and cancellation. runner/frame.mjs owns worker deadlines; runner/harness.py defines the supported AST policy. Python runs in browser Pyodide, not host Python.
  3. src/domain.mjs — assess, verdict and makeReport compare outputs, withhold passes for incomplete evidence and record sources/cases/policy hashes. The UI renders these records and exports JSON.

To change this, start here

  • Task contracts, visible/challenge cases and teaching candidates: src/fixtures.mjs.
  • Visual layout and spacing: src/App.tsx and src/styles.css.
  • Result semantics and provenance: src/domain.mjs, with tests in tests/domain.test.mjs and tests/provenance.test.mjs.
  • Optional live provider: server/repair.mjs. Never add credentials to source or this map.

A practice to reuse

Make the evidence explicit before declaring success. An initial browser-test wait could read the original's intermediate verdict before candidate verification finished. tests/browser.mjs → waitDone now waits for the run to end. Separately, a sorted-list fixture used an unsupported generator expression: the evaluation correctly stopped, and the fixture was rewritten within the existing policy. A green headline must correspond to the state and behavior actually checked.

Run again

In the project directory, run start-local.ps1, then open http://127.0.0.1:4100. Both local ports 4100 and 4101 are required. The real-browser checks are node tests/browser.mjs; the extended owned-fixture evaluation adds --evaluate.
