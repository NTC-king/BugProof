# Evaluation protocol

This measures the verification application on self-authored supported functions. It does not measure live-model accuracy, real-world correctness, benchmark superiority, profitability or winning odds.

The extended set has 12 tasks, each with an original faulty function, inadequate teaching candidate, reference and explicit visible/challenge expectations. Six tasks add an extra inadequate candidate: 30 known faulty variants and 12 references. All are hand-authored, not observed model outputs.

Build, then run `node tests/browser.mjs --evaluate`. The script drives the actual UI and actual browser Python. Each candidate has a downloaded report. The aggregate separates expected-correct labels, observed verdicts, visible-example acceptance, challenge failures and exact report paths. Both versions use identical cases/policy. Do not edit expectations to make a candidate pass.

Count faulty variants separately from references. Policy-blocked or incomplete checks are not semantic successes. The script requires known faulty variants to fail declared behavior and references to pass listed cases. Visible-example acceptance can be compared with full-suite rejection using the same outcomes.

These public development fixtures are not a held-out model benchmark. A genuine model evaluation needs a separate uninspected frozen set, fixed prompt/model/budget, recorded unsuccessful attempts and exposure-aware retries.

## Actual development failures
- Initial browser testing exposed a wait that could read the original's intermediate verdict before candidate verification finished. The test now waits for completion; the first four-fixture browser suite subsequently passed.
- The first extended run stopped at the sorted-list fixture: its source used a generator expression outside the declared supported subset. Five preceding fixture groups completed. The fixture was rewritten with a list comprehension, preserving its intended behavior without loosening the execution policy. The failed run is not reported as a complete evaluation.

Latest completed results must be identified by their actual timestamp and source revision. Provider unit tests use response doubles; no live model request was performed in the initial implementation.

The 0.2 upgrade uses report schema v2 and separately saves smoke runs to `artifacts/browser-smoke-results.json`, preserving the full fixture aggregate. A controlled browser test appends a comment to one served harness response to create a policy-hash mismatch without changing function outputs. Its purpose is to verify that the app withholds a passing comparison and shows the policy warning. It is not a benchmark candidate or a live provider result. See `docs/UPGRADE_0_2.md` for actual completed timestamps and evidence audit.

The subsequent opt-in genuine model smoke test is separate: `artifacts/live/summary.json` and its linked median evidence. One real candidate passed six listed cases on 2026-10-22. Do not merge that single sample with the 42 hand-authored candidate counts or present it as held-out model accuracy. The live runner is never invoked by ordinary test commands and requires explicit consent/free-tier flags.

Version 0.3 uses schema 3. Each worker outcome includes observed Python version, implementation and Pyodide version; all reports must have matching policy/runtime metadata to pass. A second explicit test-only response mutation changes one worker's reported Pyodide version while retaining correct outputs; the comparison must become incomplete. The consent-revocation browser test intercepts a pending API request and makes no provider call. Unit/server test files run sequentially to reduce peak memory on this Windows machine. Historic genuine 0.2 live evidence is not relabeled or regenerated by these tests.

The follow-up audit validates the complete fixture/variant manifest, not just an aggregate length: every expected candidate appears exactly once, at its exact report path, with the correct reference/faulty label, expected verdict and case count. Visible-example acceptance and challenge-failure counts are recomputed from report rows. Duplicate replacement, omissions, unknown variants and incorrect metadata have dedicated regression tests. See `docs/ACCEPTANCE_AUDIT.md` for the requirement-by-requirement completion boundary.

Version 0.3.1 adds controlled browser API response doubles for malformed and complete repair metadata. The complete double is explicitly labeled test data and is never saved as a genuine AI result; no provider connection is made. Large workspace/formatting checks execute 32 declared cases after lossless compact formatting and confirm invalid imports preserve existing evidence. Prompt-exclusion regressions require every recorded visible-input hash, not merely an array of hashes. See `docs/FULL_CHECK_2026-10-24.md` for observed failures, fixes and completed run records.
